# The engine service answers from immutable packs; Postgres keeps the Stored Index for rows

Every answer the Site used to work out in TypeScript from a Stored Index held in its own memory now comes from the engine service: a small Rust HTTP service beside the Site that answers from a pack, an immutable snapshot of a repository's Index at one head that each Build writes to R2. Postgres keeps the Stored Index for what SQL does well (Commits pages, branches, pull requests, a person's commits on a day); its daily summaries are dropped. A Build walks the history once and counts Lines Changed for the Mainline first, within a time budget.

## Status

accepted (2026-10-25, owner review of the performance report; built on 2026-10-26). Amends ADR-0027: the Site no longer holds Stored Indexes in memory, the TypeScript port of the metrics and its parity test are gone, and the daily summaries are dropped. Amends ADR-0026 (one `commitscape build` per phase, sharing one engine cache) and ADR-0012 (the order and limits of the line pass). Reverses ADR-0014's rule that Rust never runs as a web server. ADR-0016 (Shared Reports) and ADR-0019's rule that no email address leaves the Builder stand.

## Context

Measured on 2026-10-25 on facebook/react (35,318 commits) and on the production server, which has two vCPUs on one core:

- **The Site did the engine's work twice.** It loaded each Stored Index from Postgres into Node memory (`loadView`) and worked out every answer with `@commitscape/data/answers`, a line-for-line port of the engine's `Analysis` held equal to Rust by a parity test. Every change to a metric was made in both languages. react's view was about 45 MB of heap; the Site's caches could reach about 1 GB; the Code screen's tree (89 to 105 ms) and coupling (39 to 49 ms) ran on the Site's one main thread, so every other request waited.
- **The Universe's query took 19 s at p50** (372 s at p95) in production: the Atlas was made from `index_files` joined to `index_commits`.
- **A cold Build walked the history three times** (`signatures`, the quick `report`, the full `report`), loaded two Stored Indexes, wrote Reports to R2 that the Site no longer read, and then ran `git rev-list` and two `UPDATE`s over every commit row to mark the Mainline.
- **The line pass counted every ref.** 69% of the lines react's pass diffed were on branches other than the default one (build branches, `gh-pages`, old releases): 61 s of one core for every commit, while the default branch alone needed a few seconds. It took every core it was given, beside the Site and Postgres.
- **The four daily-sum tables** (`index_days`, `index_signature_days`, `index_folder_days`, `index_signature_folder_days`) were written by every load and read by nothing.

## Decision

- **Each publish writes a pack.** `commitscape build` (hidden) reads the engine cache once and writes three things: the `COPY` files of export format 3 for Postgres, `meta.json` (the Report's meta, stats and people) and `pack.bin`. A pack is the resolved Index at one head, bincode compressed with zlib: commits with their Changesets and Lines Changed, files, people with their logins and colours, release tags and their commits, and each commit's Mainline bits and Main Arrival. Every email address is replaced by a number before it is written, so a person's identities can still be counted. The Builder uploads it to `packs/<repo>/<stored index>/<head>-<build>-<quick|lines>.pack` and records the key on `stored_indexes.pack`. A key is never written twice: each publish uploads a new pack and deletes the one it replaces.
- **The engine service answers from packs.** `apps/engine` (`commitscape-engine`, axum on tokio) answers every question the Site's view answered: the Data Source's screens for any Window, the Code window's tree, coupling, history and story, a folder's newest commits, Commits under a folder, a pull request's insight and the Universe's rows. Each endpoint returns exactly the JSON the TypeScript function it replaced returned. It fetches a pack from R2 once, keeps it on disk and decoded in memory (each a least-recently-used cache by size), and keeps answers by pack and question. CPU work runs on a fixed pool behind a semaphore, never on the async runtime. It takes a shared token, listens only on the private network, and never reads git: a layering rule keeps `gix` and the indexing crates out of it.
- **Postgres keeps the Stored Index for rows.** The Commit List and its search, a person's commits on a day, branches, tags, pull requests and the files at HEAD stay as rows, read with SQL. The daily-sum tables are dropped. The Report's meta and stats move to `repositories.report_meta` and `report_stats`, so the Site never reads a Report index from R2.
- **The Site holds no history.** It reads the pack key from Postgres, asks the engine service with it, and keeps only the responses it sent, brotli-packed (64 MB). `@commitscape/data/answers`, `loadView`, the parity test and the Universe's query are deleted. A repository whose Stored Index has no pack yet answers from its old Report in R2 until `node builder.mjs rebuild` builds it again.
- **One walk per Build.** The quick and full clones share one engine cache (`--cache-key`, the repository's id), so the full phase reads what the quick phase walked and fills its Lines Changed into the same Stored Index. The Mainline is worked out in Rust, in the same run.
- **Lines Changed: the Mainline first, within a budget.** The line pass counts the commits HEAD reaches first, newest first, then the rest. It never counts Bulk Commits, lockfiles or Generated Files: they are not counted, never zero. It stops after `LINES_BUDGET_SECONDS` (120); what it did not reach is counted by up to three quiet Builds a minute apart and by the next Build. The Site shows Lines Changed once the Mainline's are counted.
- **A separate service, not a Node add-on.** A napi-rs add-on loaded by the Site would save a network hop and an application. It was not chosen because the add-on's CPU and memory would be the Site's own, on a server where the Site's main thread was already the bottleneck; a crash or runaway allocation in native code would take the Site down with it; it would tie the Site's image to a native build for each Node version and platform; and it could not move to another machine. The service has its own limits, fails without taking the Site down, can run beside the Site or anywhere on the private network, and reports to Sentry with its own spans, continued from the Site's trace.
- **Rows and packs, not packs alone.** Moving the Commit List, its search and keyset pages, branches and pull requests into the pack would mean writing in Rust what Postgres already does well and was already built. The pack holds what needs a pass over history; Postgres holds what is looked up by key.

## Consequences

- There is one copy of every metric, in Rust. The CLI's Report and the engine service's answers come from the same `commitscape-report` code, held together by `apps/engine/tests/report.rs`. The TypeScript's answers on 15 cases (the fixtures and two repositories made for it, about 53,800 questions) are kept as golden files in `apps/engine/tests/golden/`, so the port can be changed only on purpose.
- Measured on react: the pack is 3.2 MB, written in 0.12 s and read in 0.03 s; decoded it is about 17 MB, and the engine service's memory was 67 MB after answering from it on every endpoint. Kept answers come back in under 0.4 ms; first answers in 0.2 to 84 ms; the Universe's rows in 98 ms (the query took 14 s on the same machine). Through the Site, a repository page drew in 522 to 587 ms cold (645 to 665 ms before), and the Site's memory no longer grows with each repository viewed.
- A cold Build of react through the Builder on two cores published its first Report in 12.6 s and finished in 17.9 s; a warm one took 3.1 s. The line pass on one core went from 61 s to 49 s for every commit, of which the Mainline took 5.7 s.
- What it costs:
  - A third application to deploy, configure and watch (a 48 MB distroless image, a volume for packs), and two settings the Site cannot start without (`ENGINE_URL`, `ENGINE_TOKEN`).
  - One HTTP round trip for every answer the Site has not kept: 1.5 to 2.5 ms through Node's `fetch` on the same server.
  - When the engine service is down, a repository's screens answer 503; the Commit List, which is Postgres, still answers.
  - A pack in R2 per published Build (2 to 3 MB for react; replaced packs are deleted), and up to `PACK_DISK_GB` of disk for the engine service's copies.
  - The pack's format is versioned. A change to it means building every repository again with `node builder.mjs rebuild`; packs are never migrated.
- Postgres still grows with each repository's history; the daily sums no longer add to it.
